# Customer access, bank verification and app updates — 0.16.0

Install this signed update over the existing customer app once. Do not uninstall, reset or enroll the customer again. In the extracted Windows update ZIP, connect the enrolled phone and run **START-HERE.cmd**. The signing identity, encrypted account and device owner stay in place.

## Improvements

1. **Open Loop Secure on a paid/unrestricted phone.** MainActivity now opens normally rather than automatically entering kiosk mode when its package is permitted. Unlock checks retain the app's own permitted package instead of removing it and causing Android to finish its task. Restriction is started explicitly only when a verified account requires it. The app is not made the default launcher.
2. **Get verification codes while paying.** Checkout has Messages / OTP and Banking app buttons. A restricted phone temporarily permits its genuine default SMS handler during a live checkout, with a ten-minute lease. No SMS-reading permission is requested and no OTP is read or uploaded. Approved bank applications remain available. Copy the code and use Back or Recents to return to the existing checkout. Closing checkout removes the temporary SMS access; the payment does not grant unrestricted phone access.
3. **Bank challenge compatibility.** The exact HTTPS bank host `dsecure.tymedigital.com` is permitted on port 9643 for its `/acs/` verification paths; arbitrary hosts and ports remain blocked. Bank verification pop-up WebViews remain separate, preserving their challenge POST/session while switching to Messages or a bank app. TLS certificate validation stays enabled.
4. **Recover from failed checkout.** A bank connection failure now shows recovery controls instead of only a WebView error. Check the payment result first, then return to the secure checkout, open the original link in a browser on an unrestricted phone, or copy the same customer link to another device. The app does not replay a bank challenge POST or mark a failed page as paid.
5. **Understand payment status.** The Payments screen now has Pay online and Check online payment actions, a last-check status, and the existing bank EFT controls. Pending, paid, review-required and unavailable states have different explanations. Account refreshes preserve the Payments page. Recently verified checkouts return their receipt instead of immediately creating another link.
6. **Protected automatic updates.** Once 0.16.0 is installed, an enrolled device-owner app checks on unmetered Wi-Fi approximately every six hours, subject to Android scheduling. It waits for an idle phone with adequate battery and defers while the app or a checkout is active. It fetches a short-lived, device-bound Ed25519-signed update manifest, downloads from the fixed HTTPS storage origin, verifies exact length/SHA-256, package name, strictly newer version and the existing APK signing identity, then installs through Android PackageInstaller. The account is not re-enrolled. **Device info / management status → App updates → Check and install** runs a manual check on the current connection. Android/manufacturer installation restrictions are reported; failed downloads never replace the installed app.

## Current payment observation and limits

The existing customer's stored payment-link status was checked directly with iKhokha during this repair and returned **UNPAID** for R300. This is the state of that recorded attempt at the time of the check; reaching a card or OTP page alone does not prove payment. The owner reported that a virtual-card flow worked and that the physical-card flow failed only in Loop Secure. A successful physical-card challenge and final provider PAID confirmation still need to be checked on the actual phone after updating.

`ERR_TUNNEL_CONNECTION_FAILED` is a connection failure to the bank challenge, not an instruction to bypass verification. The bank's port-9643 root endpoint was reachable from the build environment; that does not establish connectivity on the customer's phone. If the physical card still fails in the updated embedded checkout, use **Open in browser** while the phone is unrestricted (the owner reported Chrome working), or use the same copied link on another device. Keep online card payments enabled in the bank and check network/VPN/proxy settings when relevant. Do not pay again if the bank debited the account while iKhokha is still confirming it.

Saved-card tokenisation is not exposed in the iK Pay API guide currently supplied/published. Loop Secure therefore does **not** add a local card-number/CVV store or a fake save-card option. Customers may use any saved-card facility offered directly by iKhokha's hosted checkout; a Loop Secure saved-card feature needs a documented, enabled provider tokenisation service. Existing direct EFT claims continue to require manual settlement review. SMS/email payment alerts are not newly configured by this update.

References: [Android PackageInstaller device-owner behavior](https://developer.android.com/reference/android/content/pm/PackageInstaller.Session#commit(android.content.IntentSender)), [iK Pay API documentation](https://developer.ikhokha.com/overview).
